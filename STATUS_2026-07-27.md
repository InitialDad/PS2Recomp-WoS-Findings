# Status update, 2026-07-27

A dated snapshot of where the Way of the Samurai (`SLUS-20407`) static-recompilation
port actually stands, written so the claims in this repo can be checked against a
point in time rather than read as evergreen truth. Everything below is measured.

## The early-boot hang is fixed

It was memory corruption, and it turned out to be a single systemic allocator
cause rather than the many downstream hang sites it presented as (malloc /
Deci2 / `0x8dcb00` / `0x152c78`). Patching the individual sites was a trap; each
fix just moved the freeze somewhere else. The reference signature of that failure
is preserved in [`logs/boot_p7i.log.gz`](logs/boot_p7i.log.gz), 1,060 samples of
the EE thread frozen at `pc=0x1d1050` inside the game's dlmalloc smallbin scan.

The runtime now sustains its main loop: **+2,803 frames** in the best drive, no
bad dispatches, no bad allocations, vblank ticking.

## The blocker is now rendering, not memory

The screen is a flat clear colour, but:

- texture uploads do reach VRAM (a 512x512 PSMT4HH transfer, a 256x128, and
  several 8x2 CLUT loads, all host-to-local),
- 96 `TEX0` writes and 96 `prim=6` sprite kicks occur per title screen.

So the defect sits downstream of upload: rasterisation, sampling, or the draw
target.

## A GS note that generalises beyond this game

Way of the Samurai uploads its title texture as `PSMCT32` at `bp=0x1A40` and then
samples it as `PSMT8` from the same `tbp0`. That looks malformed and isn't, it is
the standard idiom: `256*128*4 = 131072` bytes is exactly `512*256` PSMT8
indices, so the game is pushing an 8-bit texture through a 32-bit BITBLT for DMA
throughput and expecting the GS to unswizzle on sample. Any GS implementation has
to make the two formats address the same physical bytes for that to work.

## What we got wrong about it, and how it resolved

We nearly reported this as a confirmed recompiler bug, and it would have been
wrong. Our probe printed `rawIndex=0x00` and we read that as a broken swizzle,
but the probe was capped at the first 24 samples and all 24 landed at
`u<=2, v<=1`, the top-left corner, where index 0 is perfectly legitimate. That
measurement cannot tell a broken swizzle from a blank corner.

Replacing it with an aggregate over every sample settled it. For the title
texture (`psm=0x13 tbp0=0x1A40`):

| samples | UV rectangle reached | non-zero | distinct indices |
|--------:|----------------------|---------:|-----------------:|
| 1,000     | `u=[0..250] v=[0..1]`   | **0.00%**  | 1   |
| 500,000   | `u=[0..480] v=[0..255]` | **35.21%** | **256** |

**The PSMT8 read works and the swizzle is exonerated.** All 256 index values
appear across the full 512x256 texture. Note the first row: even at 1,000 samples
the probe had only reached `v=[0..1]` and still read 0.00% non-zero, which is
exactly how the original 24-sample probe fooled us. The top rows of the title art
are simply blank.

So the black screen is caused by something downstream of texture sampling. That
is where the search goes next.
